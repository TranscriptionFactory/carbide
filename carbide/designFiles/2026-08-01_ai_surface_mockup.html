Hybrid retrieval

Retrieval fans out to two engines in parallel: SQLite FTS5 for exact term matches and the local embedding index for semantic neighbors. Results merge through Reciprocal Rank Fusion before scope filters apply.

The fusion weights are still hand-tuned and we have not measured how block-level matches interact with whole-note scores, which probably explains the duplicate-source problem.

  • RRF constant k=60, unvalidated against [[rrf-weights]]
  • Block hits folded in after note-level dedup — see [[embeddings-pipeline]]

Pins → proposal phases

0

Run kernel

One run registry owns every stream: the inline menu finally gets a Stop control, one provider resolver serves all surfaces, and closing a surface no longer kills the run.

1

Unified sessions

One session store, one history. Kind badges (⌁ inline / ▤ note / ◈ chat) mark provenance; "Continue in chat" promotes an inline run by session id, not by copying context.

2

Recipes route, context composes

Recipe chips appear in every surface — including the panel, which has none today. A recipe declares its context sources (selection, retrieval, …); the dock only decides defaults.

3

Proposal queue

Every AI edit is a first-class proposal: hunks, target paths, session provenance, accept/reject via the action registry. Inline decorations, panel diffs, and agent changed-files are three renderings of this one queue.

4

rag → retrieval engine

Citations and hybrid retrieval come from a pure RetrievalPort the assistant consumes — the same pipeline in-app and over MCP, with the agent transport moved out of the retrieval module.

5

Panel as projection

The bottom tab is the chat component scoped to the active note (▤ This note chip) — same sessions, same presence, same proposals. No separate history file, no separate store.

6

Ambient reactor

Opt-in proactivity: a reactor watches note/editor stores and enqueues suggestions into the same session store — the "daemon feel" with zero new infrastructure.

Presence — the ✦ Assistant · provider · status chip — repeats in all three surfaces by design: one identity, projected. Frame content is illustrative; layout and components mirror the current app shell.
